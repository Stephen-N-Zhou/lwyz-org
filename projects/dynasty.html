DYNASTY / A BUILDING JOURNAL

从本地游戏，
到掌中世界。

一个历史策略游戏的开发记录：如何构建可复现的规则引擎，用私有网络连接手机，并为触屏一点一点打磨交互。

Python + WebTailscale Serve手机 / iPad项目手记 · 非在线试玩
本篇导览项目概览系统架构手机连接触屏设计调试与微调实际画面

01 / THE PROJECT

一个游戏，
也是一次系统实践。

Dynasty 是以中国历史为背景的单人策略游戏：玩家管理城池、部署武将，并在不断变化的局势中作出决策。

它从文字和本地规则出发，逐渐加入战略地图、战斗画面以及触屏操作。这里重点记录实现过程：让同一套游戏逻辑同时服务命令、本机网页和移动设备，并尽量让每个结果都可以解释、测试和复现。

本页为开发案例，不是公开的游戏入口；下面的命令和域名均为通用示例。

02 / SYSTEM DESIGN

让规则只有一个答案。

界面负责输入与呈现，规则引擎负责判定。这样无论从命令还是地图发起操作，都不会各自维护一套游戏结果。

01 / INTERFACE浏览器与触屏

HTML、CSS、JavaScript 展示状态；地图使用 SVG，战斗画面使用 Canvas。

02 / LOCAL SERVICE本机 HTTP + JSON

本地服务接收请求、校验来源与操作，再调用游戏命令并返回状态。

03 / ENGINEPython 规则与数据

引擎验证行动、推进回合与计算战斗；剧本和平衡参数由数据文件组织。

把计算和表现拆开

战斗动画依据引擎产生的战报播放，而不是在浏览器里重新计算胜负。战斗预估复用核心规则，并使用独立随机源，避免试算消耗正式游戏的随机序列。引擎记录随机种子与计数器，让相同状态和指令更容易重现问题。

存档、并发与安全边界

存档写入使用临时文件和替换，降低中途写坏文件的风险；服务对操作加锁，避免并发请求同时修改状态。请求还会检查 Host、来源和特定请求头。但这些检查不是用户登录系统：能访问服务的人仍可能操作游戏，需要另靠网络访问控制保护。

AI 与确定性规则各司其职

规则、资源变化和战斗结果由引擎决定；自然语言可以用于受约束的叙事或互动。将可变的表达和可验证的状态分开，既方便丰富体验，也便于定位错误。

03 / PRIVATE ACCESS

手机如何连接电脑上的游戏？

电脑运行游戏服务，手机与 iPad 通过 Tailscale 私有网络访问；浏览器看到的是 HTTPS 地址，游戏服务本身仍只监听电脑的本地回环地址。

手机 / iPad 浏览器→Tailscale 私有网络→电脑上的 Serve→127.0.0.1:8777 游戏服务

准备：先连接设备

  1. 在电脑和手机或 iPad 安装并登录 Tailscale，确认设备已连接到同一个 tailnet，且访问策略允许连接。
  2. 根据需要在管理端启用 MagicDNS 与 HTTPS；查看 Serve 输出，获取自己的 HTTPS 主机名。证书和设备名称有隐私影响，公开文章和截图不要展示真实主机名或地址。
  3. 在电脑保持游戏进程运行，并防止电脑休眠。手机上打开 Serve 提供的 HTTPS 地址；若使用其他账户或设备，先确认其访问权限。

相关步骤会随 Tailscale 版本和管理策略变化，可对照 官方本地服务访问指南与 Serve 命令文档。

示例：保持服务在本机，再开启私网代理

在游戏代码目录的 PowerShell 中启动服务。把占位符替换为 Serve 给出的完整主机名，不含 https:// 或端口；这里的地址不是实际设备信息。

$TsHost = "YOUR-DEVICE.YOUR-TAILNET.ts.net"
python dy_server.py --port 8777 --allow-host $TsHost

在另一个终端开启前台代理：

tailscale serve 8777

以命令输出为准，在手机浏览器访问对应的 HTTPS 地址。前台 Serve 结束时可用 Ctrl+C 停止；如需后台运行或停用特定代理，请先查看当前版本的官方文档，避免影响已有配置。设备首次配置可能需要管理员启用相关功能。

私网不等于应用登录

Tailscale Serve 面向被允许访问的 tailnet 设备；它不是公开部署方案，也不会替代应用级身份认证。只允许可信设备访问，不要为了方便改用公开的 Funnel、开放路由器端口或关闭 Host 校验。参考 Serve 与 Funnel 的区别。

连接不上时，按层排查

  • 本机也打不开：先确认 Python 服务仍在运行、端口正确，查看终端报错。
  • 手机连不上：检查两台设备是否在线、同一 tailnet 的访问策略、Serve 是否仍运行，以及电脑是否休眠。
  • 能连接却返回 403：检查浏览器使用的主机名与 --allow-host 是否完全一致；默认 HTTPS 地址避免非默认端口导致来源检查不匹配。不要靠关闭校验解决。
  • 页面能开但操作失败：查看浏览器网络请求和服务端日志，区分来源检查、请求格式和游戏规则错误；分享日志前先移除设备名、地址和存档内容。

04 / MOBILE & TABLET

触屏不是缩小版桌面。

一张大地图要同时容纳点击、拖动、页面滚动和缩放。核心工作是让这些动作互不抢夺，并给不同屏幕留下足够空间。

01 / LAYOUT

手机、平板分别考虑

根据视口宽度和方向调整，而不只按设备名称判断：窄屏将多列面板堆叠；较宽屏保留更多并排信息。战场还针对竖屏和矮横屏分别布局，平板分屏也要纳入检查。

02 / TOUCH

地图的手势分工

双指缩放和平移地图；单指水平拖动地图、垂直滚动页面。移动超过阈值后判断方向，避免轻微抖动误触。另提供缩放、复位和全屏按钮。

03 / NAVIGATION

返回与长按

返回操作优先关闭菜单、面板或当前视图；长按约 550 毫秒可触发上下文操作，移动超过容差则取消，并抑制随后的误点击。

04 / COMFORT

留出安全区域

战斗界面使用 safe-area inset 避开刘海和底部手势条；窄屏操作按钮增加可触碰高度。输入框在粗指针设备使用 16px 字体，减少 iOS 聚焦时的意外放大。

几个值得保留的实现细节

/* 触屏输入：降低 iOS 自动放大的概率 */
@media (pointer: coarse) {
  input, select, textarea { font-size: 16px; }
}

/* 重要控件避开系统遮挡 */
.controls {
  padding-bottom: max(12px, env(safe-area-inset-bottom));
}

这是提炼后的示意代码，不是完整样式。游戏实际还使用动态视口单位、方向媒体查询以及滚动边界控制；调整时需要分别检查浏览器地址栏收起、横竖屏切换和系统手势。

一个需要继续改进的取舍

当前地图手势实现会拦截页面级缩放，以便双指操作地图；这可能影响依赖浏览器放大的用户。更好的后续方向是把手势限制在地图区域，保留页面缩放并测试辅助技术，而不是把禁用缩放当成通用最佳实践。

05 / FINE-TUNING

体验来自许多小的调整。

没有一个断点或一次测试能覆盖所有设备。把问题拆成可观察的行为，再一次只调整一个变量，更容易知道改动是否真的有效。

  1. 先量空间，再改布局

    分别检查手机竖屏、横屏、iPad 全屏与分屏：标题是否换行、面板是否溢出、底部控件是否被遮住。用宽度和可用高度共同判断，不把 iPad 永远当作桌面。

  2. 区分点击、拖动和长按

    从轻触、慢拖、斜向滑动、双指缩放到中途抬手逐项测试。地图的方向锁定约 8px，长按移动容差约 10px；这些是当前实现的起点，不是所有设备的万能数值。

  3. 测试返回与中断

    打开面板后按返回、旋转设备、切换应用再回来；确认当前视图、滚动位置和正在进行的战斗不会因为意外关闭而丢失。

  4. 性能与动画按设备观察

    战斗动画使用 requestAnimationFrame，缓存绘制资源，并考虑减少动态效果的系统偏好。实机观察卡顿、内存和耗电，再针对具体瓶颈调整；不凭模拟器宣称固定帧率。

  5. 记录问题，分层定位

    先区分触摸事件、布局、网络请求和规则计算。地图提供 ?touchdebug=1 调试入口；复现时记下设备、方向、操作步骤及预期结果，分享前清理敏感信息。

  6. 让修改可回归

    规则、服务器和战斗有自动化测试；修改后运行相关测试，再用真实手机和平板检查触摸、键盘、横竖屏和安全区域。浏览器模拟器有帮助，但不能替代实机。

一个实用的微调循环

复现 → 定位 → 最小改动 → 自动化回归 → 多尺寸和实机复查。 例如按钮难点中时，先检查可点击区域与相邻间距，而不是立即放大整个面板；地图误触时，先记录手指移动路径，再调整阈值。每次保留修改前后的观察，避免改善一个设备却让另一个设备退步。

文中区分了当前代码已有设计与建议的后续检查；实际设备表现仍需在对应手机和 iPad 上验证。
